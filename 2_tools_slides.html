06 / 19

Verbs as intents, not primitives.

An intent like view can absorb related needs through optional parameters; a primitive locks you into one input shape.

5 primitives 
read_file(path)
list_dir(path)
search_text(path, pattern)
search_files(dir, glob)
file_tree(path)
1 intent 
view(
  path,
  view_range?,
  grep?,
  glob?,
  tree?,
)

Each carries information the model can't infer from the tool name.

✅ keywords: ["kubernetes", "ingress", "ssl"]
B. Cross-references
For SSH, use run_remote_command instead.
For long-running, use run_command_task.
C. Hidden behavior
If output exceeds 300 lines it will be
truncated and saved to a file.

Part 3

Parameters & schemas.

The actual contract between the agent and your tool.

12 / 19

Reject unknown fields.

The model occasionally hallucinates parameters (cmd instead of command). Silently ignoring them produces calls that succeed but do the wrong thing.

Silent acceptance 
run_command(
  cmd: "ls",       // typo, ignored
  timeout: 30
)
→ runs "" with timeout 30
Structured error 
run_command(
  cmd: "ls",
  timeout: 30
)
→ ERROR: unknown field "cmd".
   Did you mean "command"?
13 / 19

Validate at the boundary.

Without explicit limits, malformed inputs (empty arrays, very long strings, wrong types) tend to leak through and produce confusing failures downstream.

// Validation rules added to search_docs:
- Max 32 keywords           (else: too unfocused)
- Max 128 chars per keyword (else: probably a sentence)
- Max 1024 chars total      (else: probably pasted a doc)
- Reject empty keywords     (else: returns everything)

// On violation:
ERROR: "keywords" field has 47 entries (max 32).
       Try fewer, more focused keywords.
14 / 19

CLIs enable progressive disclosure.

Tool definitions load into context on every turn — even when the capability isn't needed. A complex capability easily expands to 5+ tools. Behind a CLI invoked through run_command, the same capability sits dormant until the agent reaches for it; the system prompt only teaches enough to know it exists.

✗ As tools — always loaded 
// 5+ tool defs per capability,
// every turn, every session
ak_search, ak_read, ak_write,
ak_list, ak_remove, …

board_list, board_create,
board_update, board_get,
board_assign, …
✓ As CLIs — referenced in the prompt 
# Knowledge Store: `stakpak ak`
# Use ak freely as long-term memory.
stakpak ak search [path]
stakpak ak read <path>
stakpak ak write <path>
# …

# Task Management: `stakpak board`
# Use for multi-step / cross-session work.
stakpak board mine
stakpak board create card …
stakpak board update card …
# Full schema: `stakpak board --help`
The prompt teaches names and the workflow shape. The rest of the schema enters context only when the agent runs --help.
15 / 19

The response is part of the contract.

Destructive tools can produce enough output to undo themselves. Same idea applies to str_replace, which returns a unified diff.

Irreversible 
remove(path: "/tmp/data")
→ "deleted"
Soft-delete + backup path 
remove(path: "/tmp/data")
→ "backed up to
   .stakpak/session/
   backups/abc123/
   tmp/data"
16 / 19

Long-running ops tend to need a state machine.

A single async tool returning a task_id leaves the agent without a way to query, wait, or cancel. The async subsystem grew into 5 coordinated tools for one capability.

Dead-end 
run_async(cmd) → task_id

(now what?)
Coordinated tools 
run_command_task(cmd)  → id
get_all_tasks()        → table
get_task_details(id)   → output
wait_for_tasks([ids])  → blocks
cancel_task(id)        → kill
17 / 19

A tool doesn't have to do anything.

The schema can be the entire value. The host handles the rest.

// Tool definition
ask_user(questions: [
  { label, question, options: [{ value, label }],
    multi_select: bool }
])

// Implementation in the MCP server
return error("INTERACTIVE_REQUIRED — handled by host")

// What actually happens
1. Model emits ask_user(...)
2. Host (TUI) intercepts before the tool runs
3. Host renders a real radio/checkbox prompt
4. User picks → host injects result as tool response
5. Model continues with the structured answer
The schema is the affordance. The MCP handler is a stub.
18 / 19

What this case study suggests.

Ten observations from 12+ months of iteration. Refer back as needed.

Shipping with 2 tools is a viable starting point. New tools tend to accrete from observed failure modes, not imagined ones.

Names drive selection. Descriptions drive correct invocation. Both matter, in that order.

Verbs as intents (view) tend to age better than verbs as primitives (read_file).

Long-running operations tend to need a coordinated set of tools, not a single async call.

Mutating tools can use their response to make their own undo cheap (backup paths, diffs).

Description length tended to follow a U-curve: generic → bloated → tightened in a single pass.

Validating at the tool boundary with structured errors was more useful than relying on prompt-level instructions.

Some tools are pure protocol. ask_user is just a schema; the host UI does the work.

Optional or context-dependent capabilities (knowledge store, task board) were exposed as CLIs invoked through run_command, so 5+ tool definitions per capability didn't sit in every context window.

Across ~17 tools and ~178 commits, design changes were continuous — closer to product work than to setup work.
